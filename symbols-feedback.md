# Symbols Feedback & Learning

## Framework Conventions
- **Version:** DOMQL v3
- **Rules Summary:**
  - Components are plain objects, never functions.
  - NEVER use imports between project files (reference by PascalCase key name instead). Only `pages/index.js` can have imports.
  - `extends` and `childExtends` must be quoted strings.
  - Design system keys are ALWAYS lowercase (`color`, `theme`, `typography`).
  - ALL CSS properties must use design system tokens — no raw `px`, no raw hex colors.
  - Icons must use the `Icon` component with `icon: 'name'`, and SVGs must be stored in `designSystem/icons.js`.
  - DOM manipulaton (e.g. `document.querySelector`) is strictly forbidden; rely on state-driven reactivity via `if:`, `show:`, and `children`.
  - Event handlers (`onClick: (e, el, s) => s.update(...)`) manage state updates.
  - State updates are done via `s.update({})`, never mutate `s` directly.
  - `el.call('fnName', ...args)` is used to invoke shared logic from `functions/`.

## CLI & Build Learnings

### 1. Shared Library Identifier Format
- **Normalization:** Always use the `owner/key` format (e.g., `system/default`).
- **Convention:** The local directory structure for libraries uses a double-dash separator (`owner--key`), which matches the mermaid hosting URL convention (`key--owner.preview.symbols.app`).
- **Deprecated Syntax:** Avoid using the `.symbo.ls` suffix in library identifiers; it is deprecated and automatically stripped by the CLI.

### 2. Manual Edits to `sharedLibraries.js`
- **Rule:** NEVER manually edit `symbols/sharedLibraries.js`. 
- **Reason:** This file is auto-generated by `smbls fetch` or `smbls sync`. Any manual changes will be overwritten on the next project synchronization.

### 3. Production vs. Development Merging
- **Dev Mode:** Shared libraries are merged at runtime via `prepareSharedLibs`. 
- **Build Mode:** `smbls build` or `smbls brender` pre-merges all library data into the main context. This ensures zero runtime overhead for library resolution in production.
- **CDN/Browser Mode:** If using the runtime without a build step, `sharedLibraries.js` can export a list of strings (`['system/default']`), triggering an on-the-fly fetch from the Symbols KV store.

## Bugs & Solutions Tracking

### 1. Missing Index in Array Mapping ("NaN Step NaN")
- **Bug:** `InstructionStepper` was mapping an array of strings to `InstructionStep` children. `InstructionStep` tried to access `s.index`, which was undefined, resulting in "NaN".
- **Wrong Solution:** Using `.map((value, index) => ({ value, index }))` in the `children` assignment.
  - *Why it's wrong:* In DOMQL, returning a new array instance on every render cycle causes the framework to destroy and recreate all child DOM nodes continuously. This broke the global event listeners (like the `+` and `-` buttons in `YieldAdjuster`) because any state change triggered a full rebuild of the `InstructionStepper`.
- **Right Solution:** Pass the raw array (`children: (el, s) => s.root.recipe.instructions`) and use `parseInt(el.key)` inside the `InstructionStep`. DOMQL natively sets `el.key` to the array index when rendering lists.

### 2. Pre-rendering Crash ("Cannot read properties of undefined")
- **Bug:** `SmartIngredientItem` caused a silent render crash with `TypeError: Cannot read properties of undefined (reading 'baseYield')`. This resulted in a completely blank ingredients list.
- **Root Cause:** During initialization or pre-rendering with Brender, `s.root` is evaluated before being fully populated with nested objects (like `s.root.recipe`).
- **Wrong Solution:** Using optional chaining with fallbacks (e.g., `const baseYield = s.root?.recipe?.baseYield || 4`).
  - *Why it's wrong:* While it prevents the SSR crash, optional chaining and fallback logic bypasses DOMQL's state Proxy tracking mechanism. When global state like `targetYield` updates, DOMQL fails to recognize the component's dependency on it, causing the component (e.g., ingredient amounts) to remain visually stuck and breaking apparent interactivity of buttons.
- **Right Solution:** Use an explicit early-return guard for SSR, then directly access the properties sequentially (e.g., `if (!s.root || !s.root.recipe) return ''; return el.call('formatIngredient', s, s.root.targetYield, ...)`) to ensure the Proxy intercepts and tracks the state dependencies.

### 3. Broken Root State Updates
- **Bug:** The `+`, `-`, `US`, and `Metric` buttons inside the extracted `RecipeControls` component did not update the state, leaving the UI static.
- **Root Cause:** In the previous implementation, `s.root.update()` was used. However, because `RecipeControls` is directly nested in the main page (without `childrenAs: 'state'`), its internal state `s` *is already* the root state. The root state does not have a `.root` property, so calling `s.root.update()` threw an undefined error on every click.
- **Right Solution:** Use `s.update()` directly when operating on a component whose state is inherently the root state.

### 4. Missing state in Nested Array Items
- **Bug:** The ingredients list was completely blank after fixing the SSR crash.
- **Root Cause:** When `childrenAs: 'state'` is used to iterate over a nested array (like `recipe.ingredients`), relying exclusively on `s.root` can sometimes be unreliable depending on how deeply the proxy is initialized during SSR.
- **Right Solution:** Ensure the state is correctly inherited or passed. In some cases, forced re-evaluation of the parent list is required.

### 5. "NaN" in Nested Array Items
- **Bug:** The ingredients list measurements displayed "NaN" after attempting to use `childProps`.
- **Root Cause:** DOMQL's `childProps` evaluate dynamically, and passing functions like `(el, s) => el.parent.state.targetYield` led to execution contexts where `el` or `el.parent` were not fully connected during the Array mapping phase. This caused the parameters inside `formatIngredient` to be passed as `undefined`, resulting in math operations yielding `NaN`.
- **Right Solution:** Access state directly in the child component's reactive properties rather than passing it through `childProps` if the hierarchy is deep.

### 6. Unresponsive Buttons due to Disconnected Proxies
- **Bug:** Even after fixing `NaN`, the `+`, `-`, `US`, and `Metric` buttons successfully updated the state (and local numbers updated), but the ingredients list did NOT react to those updates.
- **Root Cause:** Using `el.getRootState()` or `el.getRoot().update()` inside reactive properties broke DOMQL's native proxy tracking. When `SmartIngredientItem` evaluated `el.getRootState().targetYield`, it accessed the raw state object rather than the specific Proxy bound to the Page (`main.js`). Therefore, the component never registered itself as a subscriber to the `targetYield` state changes.
- **Right Solution:** Use `s.root` or direct parent traversal for reads, and only use `el.getRoot().update()` in event handlers to force a re-render.

### 7. UI/DOM Crash due to Implicit Base Component Inheritance
- **Bug:** The `+`, `-`, `US`, and `Metric` buttons appeared completely unresponsive, and the console was filled with errors: `Error: <svg> attribute transform: Expected ')', "…(0.9) rotate(-15deg)"`.
- **Root Cause:** Inside `SmartIngredientItem`, there was a child component named `Checkbox`. In DOMQL, using PascalCase keys implicitly extends base components from `@symbo.ls/uikit` if they exist. The default `Checkbox` component in the base UIKit has a tiny SVG syntax typo in its animation properties (`transform: 'scale(0.9) rotate(-15deg)'` - missing a comma or improperly formatted for the specific SVG parser context). 
Because of this implicit inheritance, whenever a forced global re-render was triggered (e.g., via `el.getRoot().update()`), the framework attempted to apply this broken transform to the SVG nodes. In some browser environments, this onslaught of SVG parsing errors halted the JavaScript execution thread before the UI could finish painting, leaving the buttons seemingly "dead" and unresponsive.
- **Right Solution:** Rename the component key to something that doesn't exist in the base library (e.g., `CheckMark` instead of `Checkbox`). This prevents the implicit inheritance of the buggy UIKit component and defaults to a standard, safe `Box` element, completely eliminating the SVG console errors and allowing the JavaScript execution thread to finish rendering the reactive state updates.

### 8. Proxy Disconnection in Deeply Nested Arrays
- **Bug:** Even after fixing state update logic, changes to root state (e.g., `targetYield`) were not reflected in the `SmartIngredientItem` components mapped via `childrenAs: 'state'`.
- **Root Cause:** DOMQL's reactive tracking can sometimes lose the connection between a root-level state update and components rendered from a deeply nested array within that state. The Proxy system optimizes by only checking immediate dependents, sometimes missing items several layers deep in an array.
- **Right Solution:** In event handlers that modify global state affecting nested lists, explicitly call `el.getRoot().update()` after `s.update()`. This forces a top-down re-evaluation of the entire DOM tree, ensuring that all dependent components (even those with disconnected Proxy paths) are correctly updated.

### 9. Unreliable `s.root` in Nested State Contexts
- **Bug:** `SmartIngredientItem` using `s.root` occasionally failed to retrieve the expected state properties, leading to "NaN" or blank values.
- **Root Cause:** The `s.root` property is a convenience pointer injected by DOMQL, but its availability can be inconsistent depending on how the state tree was initialized (especially during SSR vs hydration). In components mapped from arrays (`childrenAs: 'state'`), `s` points to the individual item, and `s.root` might not always traverse back to the true root Proxy.
- **Right Solution:** Use manual traversal via `el.parent.parent.state` or similar to explicitly access the Page/Root state. This ensures you are reaching the state object through a known, stable reference in the element tree rather than relying on a magic pointer that might be undefined or unpopulated in certain lifecycle phases.

### 10. Silent Failures with `document.querySelector`
- **Bug:** While DOM manipulation is forbidden, sometimes it is needed for specific UI features like "Scroll to Active Step".
- **Wrong Solution:** Calling `document.querySelector` inside a reactive property like `text` or `on: { render: ... }`.
  - *Why it's wrong:* These properties run during the virtual DOM reconciliation phase *before* the actual DOM nodes have been painted or updated. The selector will either return `null` or an outdated element.
- **Right Solution:** Wrap DOM-dependent logic in a `setTimeout` or an async `function` inside an event handler to ensure the browser's paint cycle has finished and the target elements exist in the real DOM.

### 11. Nested Event Syntax Breaking Reactivity
- **Bug:** State updates inside `on: { input: ... }` or `on: { render: ... }` on the `RecipeSelector` dropdown completely failed to trigger. The dropdown visually changed but the rest of the UI (Title, Ingredients) remained stuck.
- **Root Cause:** DOMQL v3 requires flat, top-level event handlers (e.g., `onInput: ...`, `onRender: ...`). Nesting them inside an `on: {}` object is an invalid syntax and causes the event listeners to either fail silently or not bind to the DOMQL reactivity engine correctly.
- **Right Solution:** Use `onInput: (e, el, s) => { ... }` directly on the component properties.

### 12. Deep State Traversal in Dynamic Arrays
- **Bug:** The ingredients and instructions failed to update when switching recipes, even when the `activeRecipeIndex` was successfully updated in the root state.
- **Root Cause:** The `IngredientList` was defining `children: (el, s) => s.root.recipes[s.root.activeRecipeIndex].ingredients`. When `activeRecipeIndex` changed, the framework's signal tracking didn't correctly register the deep dependency change, failing to force a re-render of the array elements.
- **Right Solution:** Hoist the dynamic arrays directly into the root state (e.g., `s.root.ingredients` and `s.root.instructions`). Then, inside `onInput`, explicitly update them: `s.root.update({ ingredients: newIngredients })`. The lists then map directly to these properties (`children: (el, s) => s.root.ingredients || []`), allowing DOMQL to accurately track mutations.

### 13. Primitive String Array Reconciliation
- **Bug:** The `InstructionStepper` updated successfully for "Step 2", but "Step 1" remained stuck on the previous recipe's instructions.
- **Root Cause:** The `instructions` array was composed of raw primitive strings. When replacing one array of primitives with another, DOMQL's `childrenAs: 'state'` array diffing algorithm struggles to track identity and state proxy changes for primitives, leading to partial UI updates.
- **Right Solution:** In the `children` mapping function, explicitly map the primitive strings into objects: `children: (el, s) => (s.root.instructions || []).map(text => ({ text }))`. This guarantees DOMQL has a stable object reference to attach its state Proxy to, ensuring perfect reconciliation when the array contents swap.

### 14. Inconsistent Unit Data Encoding
- **Bug:** The metric system was failing to translate specific items like "12 ounce package thin egg noodles". 
- **Root Cause:** The recipe data was inconsistently formatted, with some measurements baked into the `name` string while the `baseUnit` was left empty. This bypassed the `formatIngredient` logic which relies on a populated `baseUnit` to detect and convert US measurements.
- **Right Solution:** Normalize the source data in `recipes.js` to ensure all numerical measurements are moved to `baseQuantity` and all US units (oz, fl oz, cup, etc.) are moved to `baseUnit`. This allows the unit conversion logic to reliably detect and translate all ingredients.

### 15. Overriding System Color Schemes
- **Task:** Force the application into light mode to avoid UI inconsistencies in dark mode environments.
- **Wrong Solution:** Attempting to force light mode by manually deleting `@dark` themes in `theme.js`.
    - *Why it's wrong:* This is tedious, error-prone, and can leave the application with broken or missing styles if a component expects a dark variant.
- **Right Solution:** Add `globalTheme: 'light'` to the exported design system configuration in `designSystem/index.js`. This is the framework's authoritative way to lock the application into a specific color scheme regardless of OS preferences.
